# Single Plan-Scoped Navigation

**Status:** accepted

## Context

The application is moving from global prototype pages to one plan-scoped
navigation tree. Route semantics need to be stable before the member and admin
surfaces are migrated. There are no existing users whose bookmarks or global
route URLs must be preserved.

## Decision

The canonical route contract is:

| Route                             | Purpose                                                                                                                    |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `/`                               | Link-first entry. It may resume a locally known plan and provides a reachable path to `/setup`; it is not a plan schedule. |
| `/plans/:planId`                  | Canonical plan schedule, with one timeline/calendar view toggle.                                                           |
| `/plans/:planId/matches/:matchId` | One match and its member claim flow.                                                                                       |
| `/plans/:planId/cockpit`          | The current member's plan-scoped duties.                                                                                   |
| `/plans/:planId/teams`            | Plan-scoped team and roster administration.                                                                                |
| `/plans/:planId/assignments`      | Plan-scoped duty assignment administration.                                                                                |
| `/plans/:planId/setup`            | Plan-scoped maintenance/editing.                                                                                           |
| `/setup`                          | Creation and maintenance entrypoint when no plan context exists.                                                           |

All plan-dependent navigation stays below `/plans/:planId`. The schedule is
the plan entrypoint; it is not split into separate schedule routes. Match,
cockpit, teams, assignments, and setup are nested route slots under the same
plan context.

The encryption key is carried only in the URL fragment as `#key=<key>`. A
plan-aware link includes the plan ID in its path and preserves the key fragment,
for example `/plans/<planId>/matches/<matchId>#key=<key>`. The key is never put
in a query string, path segment, or server request. The existing shared loading
rules may also resume an in-memory or locally stored plan when no fragment is
present; that fallback does not change the canonical link shape.

Links between plan-scoped surfaces preserve the current `planId` and key
context. Links leaving a plan for the root or base `/setup` are explicit exits
from that plan context. Existing-plan links generated by setup use
`/plans/<planId>#key=<key>`, not a global route.

The global prototype routes `/dashboard`, `/assignments`, `/team-list`, and
`/cockpit` are removed after their useful behavior is migrated into the
plan-scoped routes. They are not canonical, must not receive new links, and
must not be retained as redirects. Unknown routes continue to use the existing
catch-all behavior until route cleanup changes that separately.

Regular member navigation is read/claim-focused: schedule, match details, and
the member cockpit. Teams, assignments, and plan setup are an admin UX
boundary, not an authorization boundary; authorization remains separate work.

## Rejected Alternatives

- Keeping `/dashboard`, `/assignments`, `/team-list`, or `/cockpit` as
  permanent global routes or compatibility redirects. This preserves the old
  split navigation tree and is unnecessary before launch.
- Making `/dashboard` the schedule entrypoint. The plan ID would remain
  implicit or query-driven instead of defining one canonical plan context.
- Creating separate timeline and calendar URLs. The two schedule views are one
  plan surface and use one toggle.
- Passing the encryption key in a query string or path segment. The fragment
  keeps the bearer key out of HTTP requests and preserves the established
  link-first behavior.
- Treating `/setup` as only a plan-scoped route, or redirecting the base route
  directly to a plan schedule. Creation needs a plan-independent `/setup`
  entrypoint, while an existing plan uses `/plans/:planId/setup`.
- Using route visibility as authorization. Regular/admin navigation is a UX
  distinction; access control is not defined by this routing contract.

## Consequences

- New documentation, tests, and links use only the canonical plan-scoped
  routes and fragment key shape.
- Member and admin migrations must retain the plan ID and key context when
  linking between plan surfaces.
- Capability migration must precede deletion of the four global prototype
  routes; no compatibility redirect is required afterward.
- Authorization, authentication, and richer member/admin permissions remain
  separate decisions.

## Implementation State

Pending. This ADR records the contract only. The route inventory and existing
prototype behavior are the baseline for later migration and route removal; no
runtime behavior is changed by this decision.
